# Margin v0.5.1 Integrity Hardening Design

## Objective

Ship Margin v0.5.1 as a patch release that includes the completed updater
lifecycle hardening and replaces four release-blocking risks identified by the
2026-08-15 engineering review with conservative, tested behavior:

1. A case-only title rename must never overwrite a distinct note on a
   case-sensitive filesystem.
2. Saving a note must not delete an image that remains referenced through a
   percent-encoded Markdown destination.
3. Multi-file link repair must detect external changes before replacing another
   note and must retain recoverable content if a late conflict occurs.
4. Release tooling and installer copy must describe and verify the trust it
   actually provides rather than implying unavailable publisher signing.

The release also includes the already completed updater controller, updater UI
and accessibility tests, nested-worktree test exclusion, testing documentation,
and the fresh `ENGINEERING_REVIEW.md`.

## Product constraints

- Notes remain portable UTF-8 Markdown files with optional YAML front matter.
- No database or repository-local note storage is introduced.
- Ambiguity is resolved in favor of preserving user data.
- Existing Windows, Apple Silicon macOS, and x64 Linux targets remain supported.
- In-app updater artifacts continue to use the configured Tauri signing key.
- v0.5.1 does not claim Apple Developer ID notarization or Windows Authenticode
  signing because the required certificates and release secrets are not
  currently configured.

## Design

### 1. Filesystem identity for case-only renames

The rename path will separate two questions that are currently conflated:

- Do the source and requested destination refer to the same directory entry?
- Do their names merely compare equal under a case-insensitive rule?

The path layer will use filesystem identity where both paths exist. A case-hop
through a temporary filename is permitted only when the destination is the same
entry as the source. If a distinct destination exists, the operation uses the
existing collision-disambiguation policy and does not replace it. Platform name
comparison remains a fallback only when the destination does not exist.

Tests will cover a normal rename, a genuine case-only rename, and distinct
`Foo.md`/`foo.md` entries on a case-sensitive filesystem. Tests that require
distinct case variants will skip only when the host filesystem cannot represent
the fixture.

### 2. Conservative Markdown image reference tracking

Asset cleanup will stop using raw substring searches. A focused parser will
collect Markdown image destinations while excluding fenced and inline code in
the same conservative spirit as the existing link scanner. For each local
destination it will:

1. Remove an optional angle-bracket wrapper.
2. Split query and fragment suffixes from the path.
3. Percent-decode exactly once.
4. Normalize separators and dot segments without escaping the note directory.
5. Compare the normalized relative path with direct files in the note's
   companion asset folder.

Remote URLs, absolute paths, malformed encodings, unsupported Markdown forms,
or any ambiguous parse will never authorize deletion. Cleanup may leave an
unused file behind, but it must not remove a possibly referenced file.

Regression tests will cover spaces, Unicode, `%25`, query strings, fragments,
angle-bracket destinations, malformed percent encodings, code spans/fences, and
traversal attempts.

### 3. Revalidated staged link repair

Each staged cross-note replacement will record the source path, original bytes
or digest, staged replacement, and recovery path. Immediately before replacing
each target, the commit phase will re-read the target and compare it with the
recorded source. A mismatch aborts the remaining transaction as a typed
conflict.

The recovery copy for a target will be based on the content observed at commit
time, not only the earlier planning snapshot. If a change is detected after
some targets were committed, rollback restores committed targets and preserves
the conflicting/current content in a recovery file rather than discarding it.
App-originated library mutations will remain serialized through the existing
native mutation boundary; arbitrary external editors are handled through
revalidation and recovery rather than assumed to cooperate with locks.

Tests will inject an edit between planning and commit, an edit after an earlier
target commits, rollback failure, and the no-conflict success path. A stale
target must never be silently replaced.

### 4. Release and installer trust

The release workflow will publish a deterministic SHA-256 checksum manifest for
release installers and packages. Post-publish verification will download the
assets and validate:

- every expected platform artifact and updater signature exists;
- the updater manifest version matches the tag;
- expected platform entries point to the matching release tag and artifact;
- each updater entry includes a non-empty signature;
- the checksum manifest covers each downloadable installer/package and matches
  its bytes.

The Windows, macOS, and Linux convenience installers will download the checksum
manifest and verify the selected artifact before installing it. This detects
corruption and mismatched/replaced assets within the release contract. The
documentation will distinguish this checksum verification from publisher
identity:

- Tauri updater artifacts are cryptographically signed and verified by Margin.
- macOS currently receives an ad-hoc code signature that verifies bundle
  integrity but not an identified/notarized publisher.
- Windows and Linux manual installers are checksum-verified GitHub release
  downloads, not Authenticode- or distribution-key-signed packages.

Full publisher identity remains a future operational task requiring Apple
Developer ID/notarization and Windows signing credentials. v0.5.1 will not use
copy such as "signed installer" for paths that do not provide that guarantee.

## Error handling

- Rename collisions produce a unique destination rather than replacing a file.
- Ambiguous image references retain assets and do not turn a successful note
  save into data loss.
- Link-repair conflicts stop the transaction, restore already changed notes,
  and return a clear conflict/recovery message.
- Installer checksum absence or mismatch stops installation before the existing
  app is changed.
- Release verification failure keeps the GitHub release in draft state.

## Test and validation strategy

Implementation follows test-driven development for every behavior change.
Before tagging v0.5.1, run:

- focused Rust tests for path identity, assets, and staged transactions;
- installer and release-contract script tests;
- `pnpm test`;
- `pnpm test:bundle`;
- `pnpm build`;
- `cargo test --manifest-path src-tauri/Cargo.toml`;
- `cargo check --manifest-path src-tauri/Cargo.toml`;
- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`;
- `cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings`;
- a native smoke launch when the Windows desktop is available.

The release workflow must finish successfully and its artifact verifier must
pass before the draft release is published.

## Versioning and release flow

All version-bearing files move from `0.5.0` to `0.5.1`. `CHANGELOG.md` receives
a dated `0.5.1` entry describing user-visible fixes and the updater behavior.
`PRODUCT_SPEC.md`, `TESTING.md`, installer comments, and README trust language
must match the final behavior.

The authorized publication sequence is:

1. Work on `release/v0.5.1-integrity-hardening`.
2. Commit only reviewed v0.5.1 files and push the branch.
3. Open a pull request against `main` and wait for required checks.
4. Merge the pull request after checks pass.
5. Create and push tag `v0.5.1` from the merged `main` commit.
6. Wait for the release workflow and artifact verification.
7. Publish the verified draft GitHub release.

## Acceptance criteria

- No distinct case-variant note can be overwritten by a title rename.
- A referenced encoded image survives note save and cleanup.
- A cross-note external edit causes link repair to abort or recover, never
  silently overwrite the edit.
- Installer artifacts are checksum-verified before installation.
- Release manifests, updater signatures, URLs, and checksums are validated.
- User-facing signing language is accurate for every installation path.
- The complete automated validation matrix passes.
- GitHub publishes v0.5.1 only after the release artifact contract succeeds.
