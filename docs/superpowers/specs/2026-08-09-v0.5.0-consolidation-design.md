# Margin 0.5.0 Consolidation Design

## Purpose

Margin 0.5.0 is a consolidation release. It makes the existing local-first notes product easier to maintain and more internally consistent without adding broad new product areas. AI integrations, Git history, importers, graph views, sync, unresolved-link note creation, tag editing, and tag filtering remain deferred.

The release has three goals:

1. Stabilize the build, tests, repository guidance, and library diagnostics.
2. Divide the oversized frontend, native backend, and stylesheet into feature-owned modules while preserving behavior.
3. Reconcile duplicated or incomplete existing workflows: search and Quick Open, Quick Capture, backlinks, tags, view-mode persistence, and background application lifecycle.

## Release boundary

This work ships as version 0.5.0 in one pull request with focused commits. The pull request must be merged and its required checks must pass before the `v0.5.0` tag is created. The release workflow must build and verify the signed artifacts before the draft GitHub release is published.

The release must not introduce a database, move notes into application storage, change the portable Markdown file format, or require an account. Existing YAML front matter remains round-tripped. Notes continue to use the first H1 as their canonical visible title and filename source.

## Phase 1: stability and housekeeping

### Test reliability

The Mermaid renderer integration test currently competes with the parallel unit suite. Its cold render normally takes several seconds and has crossed Vitest's five-second per-test deadline under contention. General tests will continue to mock the renderer. The real Mermaid integration file will run as a dedicated, single-worker test step so it tests the integration without competing with the rest of the suite. `pnpm test` and CI will run both groups.

### Toolchain and repository guidance

- Add an explicit `packageManager` field to `package.json` and use the same pnpm version in local guidance, test CI, and release CI.
- Use `.nvmrc` for Node in both test and release workflows.
- Update `AGENTS.md`, `TESTING.md`, `README.md`, and `PRODUCT_SPEC.md` to describe the real automated suite and current feature state.
- Remove the duplicate planned entry for code-fence language autocomplete.
- Do not add the untracked historical `ENGINEERING_REVIEW.md` to the release; its superseded findings will be captured only where they remain relevant in maintained documentation.

### Native command surface and diagnostics

The frontend will use one library snapshot command. The old frontend-facing `load_library`, `load_folders`, `load_trash`, and explicit `rename_note` commands will no longer be registered. Their underlying helpers may remain private where tests or internal operations need them.

Library indexing will return structured warnings for directory-walk failures, unreadable files, invalid UTF-8, and malformed metadata that cannot be safely interpreted. The snapshot remains usable when some files fail. The main interface will show a concise warning count without interrupting normal work. No note body or sensitive path detail will be logged or sent elsewhere.

## Phase 2: architectural consolidation

### Frontend boundaries

`src/main.tsx` will become a small entry point that selects the main or capture application. Feature code will be separated by responsibility:

- `app/`: main composition, shared application types, and top-level routing.
- `services/`: typed wrappers around native commands and application events.
- `features/library/`: library snapshots, folders, note lists, favorites, Trash, and navigation.
- `features/note-session/`: active-note loading, dirty state, queued saves, conflicts, external changes, and view-state persistence.
- `features/search/`: the shared search controller and both Search and Quick Open presentations.
- `features/capture/`: shared capture composer behavior, main-window fallback, and capture-window shell.
- `features/preview/`: Markdown preview, Mermaid, tables, tasks, link navigation, backlinks, and outline.
- `features/settings/` and `features/templates/`: existing settings, update, shortcut, and template dialogs.

The refactor will use existing React state and reducers rather than introducing a global state library. `NoteSession` will expose an explicit state model for loading, clean, dirty, saving, conflict, and error states. Feature components must depend on typed callbacks and data rather than importing the application controller.

### Native boundaries

`src-tauri/src/lib.rs` will become the application assembly point. Native code will be divided into modules for:

- library paths, containment, and portable filenames;
- library indexing, search, link graph, and diagnostics;
- note creation, saving, moving, duplication, Trash, and link repair;
- image companion folders and image imports;
- Daily notes and Quick Capture;
- window, tray, file-association, and shortcut lifecycle.

The command payloads and behavior remain compatible during the refactor except for the intentionally removed unused commands and the enriched snapshot/search results. Tests move beside the module they validate, with shared filesystem fixtures kept in a test-support module.

### Capture entry and shared composer

The capture window will use a separate `capture.html` and lightweight TypeScript entry. It must not import the editor, ReactMarkdown, syntax-highlighting languages, Mermaid, settings, or other main-workspace features.

The capture window and the in-app fallback will share one capture-composer component and one Markdown list-continuation helper. Both paths will apply the configured Daily template, provide the same keyboard behavior and status messages, and call the same typed native service.

### Styles

Global tokens, reset rules, and the application grid remain global. Feature-specific rules move next to their feature. Repeated late-file overrides for settings, capture, table controls, backlinks, and context menus will be consolidated. This is not a visual redesign: screenshots and manual checks should show only incidental spacing corrections required to remove contradictory rules.

## Phase 3: product cohesion

### One discovery model

Search and Quick Open will use one native ranked-search implementation. Ranking order is title, filename/path, tags, then body, with exact and prefix matches ahead of substring matches. The persistent search field filters the current note view; Quick Open searches the whole active library and remains keyboard-first. An empty Quick Open query shows recently updated notes. Note bodies remain inside the Rust-owned index and are not serialized to the webview.

Both presentations use the same result DTO and ranking. They may keep different shortcuts because their outcomes differ: Search narrows the current view, while Quick Open navigates directly.

### Tags

Tags remain portable YAML metadata and participate in search. Existing tags will be shown on note cards and in Quick Open instead of being deliberately removed. Editing tags and filtering the library by tag are deferred, so 0.5.0 does not add a new metadata editor or navigation section.

### One link graph

The Rust-owned index will parse both wiki links and resolvable relative Markdown links. Backlinks use that single graph, so `Linked from` reports either link syntax consistently. External URLs, anchors, absolute paths, ambiguous targets, and unresolved targets are excluded. Rename repair continues to modify only unambiguous relative Markdown links. Creating a missing note from a link remains deferred.

### View continuity

Opening another note will preserve the user's current Edit, Split, or Preview mode. Preview remains the initial mode on application launch. Per-note editor selection and scroll restoration continue to work.

### Background lifecycle

Because global Quick Capture keeps Margin running after the main window closes, the app will expose a tray menu with Show Margin, Quick Capture, and Quit. Closing the main window continues to hide it.

The frontend will keep native window state informed when a managed note becomes dirty or clean. Quit will request a frontend save flush. If every dirty managed note saves, the frontend acknowledges and the native process exits. If a save conflicts or fails, Margin shows the main window, preserves the draft, and displays the existing conflict or error state instead of exiting silently. If the webview does not answer within a bounded interval while native state says a draft may be dirty, a native confirmation explains that saving did not finish and defaults to Cancel; only an explicit Quit anyway choice may discard that draft.

## Data and error flow

1. The native library index watches the selected library and builds a compact snapshot containing summaries, folders, Trash, and warnings.
2. The frontend library feature owns the current snapshot and requests refreshes through a single-flight coordinator.
3. Search and backlink requests query the same native index and link graph.
4. The note-session reducer owns active-note requests, baselines, save queues, conflicts, and status.
5. Feature mutations update their local state immediately when safe and request a forced snapshot only when filesystem structure changed.
6. Expected operational problems return typed results. The UI keeps recoverable data visible and gives errors a stable location rather than relying only on transient console output.

## Validation

Implementation follows test-driven development for behavior changes. Required automated validation is:

- `pnpm test`, including the isolated real-Mermaid integration step;
- `pnpm build`, with no 500 kB warning for the capture entry and a materially smaller main entry than 0.4.6's 1.87 MB baseline;
- `cargo test --manifest-path src-tauri/Cargo.toml`;
- `cargo check --manifest-path src-tauri/Cargo.toml`;
- `cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check`;
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D warnings`.

Manual desktop validation must cover:

- library selection, search, Quick Open ranking, and warning display;
- note creation, editing, autosave, external conflicts, rename/link repair, move, Trash, and restore;
- wiki and relative-Markdown backlinks;
- tagged note display without front-matter changes;
- Edit/Split/Preview continuity and scroll restoration;
- capture from the global shortcut and fallback path, including list continuation and Daily templates;
- close-to-background, tray Show, tray Capture, successful Quit, and blocked Quit after a save conflict;
- Windows, macOS, and Linux packaging through CI, plus signed updater artifact verification.

## Pull request and release

The branch will contain focused commits for test/tooling cleanup, frontend extraction, native extraction, discovery/link cohesion, capture/lifecycle cohesion, and release documentation. Only files belonging to this release will be staged; the unrelated untracked engineering review remains untouched.

The PR will summarize user-visible behavior, architecture changes, validation, packaging impact, and the unchanged note-file format. After review and required checks pass, it will be merged before tagging. `CHANGELOG.md`, `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml` will all report 0.5.0 before `v0.5.0` is created. The GitHub release remains a draft until its platform artifacts and updater manifest pass the repository's verification job.
